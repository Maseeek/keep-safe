# Architecture and security

## Components

The Vercel deployment serves the mobile web application. It contains no browser cookies, passwords, or agent API credentials. The same frontend can be served by the local bridge.

The bridge runs on the developer's computer, listens on loopback, manages login request state, and connects to Chromium. The owner pairs using a private link with the owner token in the URL fragment. The app removes the fragment immediately. HTTP requests use bearer authentication; WebSocket authentication is the first message, not a URL query.

MCP and HTTP clients use a different agent token. An agent can create a login request and poll its status, but cannot approve the request, control the owner's interface, or subscribe for owner notifications.

## Pairing

A phone pairs with a one-time code. Only the owner key can create one, through `POST /api/pairing`, and the `keep-safe` command sends that key to the bridge on loopback only. A code is eight characters from a 30-character alphabet, lives ten minutes in memory, and works once. `POST /api/pair` exchanges it for a device key and is the only unauthenticated route that changes state. It shares the unauthenticated rate limit, keeps the allowed-origin check, marks the code used before its first await, and counts wrong codes: ten misses cancel every unused code. A bridge restart cancels unclaimed codes.

The pairing link carries the code and the bridge address in the URL fragment. The bridge builds it from its current public address and returns it with the code. The app removes the fragment before any network request. Neither the link, the QR code, nor the desktop pairing page contains a key. The desktop page is opened as `/#qr=CODE` on loopback. It asks `POST /api/pair/status` about that one code and learns only whether it is waiting, claimed or expired, and while it is waiting, its link.

A phone that is already paired can claim a new code without getting a new key. It sends its device ID and an HMAC of the code, keyed by the SHA-256 digest of its device key. The bridge holds that digest, checks the proof, and answers with the existing device. The key itself is never sent to the scanned address, the proof is useless for any other code, and a wrong proof simply pairs a new phone. This is how a phone moves to a new bridge address with one scan.

Device keys are stored as digests. A key expires 30 days after its last use and is renewed at most once a day while in use. Revocation is immediate. A device key cannot create pairing codes, and the agent key cannot either, so neither can add a phone.

The owner key remains bootstrap authority. The foreground bridge still prints an owner link for development. The background bridge started by `keep-safe up` prints none, so no key reaches its log.

## Routes to the phone

The bridge always listens on loopback. `--listen` adds named private addresses, which `keep-safe up` uses for the computer's Tailscale address. Every request there passes the same origin check and authentication as on loopback. Plain HTTP origins are accepted only for loopback, and for Tailscale addresses when `--tailnet-http` is given: the Tailscale range `100.64.0.0/10`, `*.ts.net` names and bare machine names. Tailscale encrypts that traffic between the owner's devices.

With Tailscale Serve the bridge stays on loopback and Tailscale terminates HTTPS for tailnet members only.

The default route is a Cloudflare quick tunnel, so a phone needs nothing installed and no shared network. It publishes the bridge on a random public HTTPS address, where device keys and pairing codes are the only barrier, and Cloudflare carries the traffic. The bridge still listens on loopback only. `keep-safe up` fetches a pinned `cloudflared` release into the configuration folder and checks its SHA-256 before use. The bridge starts it with `--tunnel`, reads the address from its log, checks that the address answers, and accepts that address as an app origin while it is current.

The tunnel process is detached and recorded in `tunnel.json`. A bridge restart adopts it when the recorded process is still `cloudflared`, serves the same port and its address still answers, so the address survives restarts and updates. The bridge checks it every five seconds and opens a new tunnel when it has ended. A recorded process ID is only ever stopped after confirming it is `cloudflared`.

The address changes when the computer restarts. There is no directory service. Instead each request notification carries the current address, which Web Push encrypts for that phone, and the service worker stores it against the bridge's notification key. The app adopts it when its connection fails, only for the computer it is paired with. A phone without notifications scans a new code, as described under Pairing.

## Live view

The phone reports its usable screen size when it starts watching. The bridge clamps it (320 to 1280 wide, 320 to 1400 tall, density 1 to 2) and opens the managed browser at that size, so websites lay out for the phone. The browser keeps its desktop identity. Clients that send no size get the earlier 390 by 720 view. Attached browsers are never resized.

Frames are captured up to ten times a second. A frame identical to the last is sent at most once a second, a busy connection skips captures, and each input triggers an immediate capture. Still pages are sampled at a third of the rate.

After a tap, Tab, Enter or a page-control focus, the bridge reads the type of the focused element and tells the phone whether it is editable and what kind of field it is. No value, label or address is read. The phone uses this to raise its keyboard. Typed characters go into a password-type field that holds one placeholder character, are forwarded at once, and are removed. Nothing typed is stored, logged or echoed on the phone. A single typed character is delivered with real key events. Longer text is inserted whole.

## Why the browser stays local

The additional spending cap is £0. A local browser avoids paid always-on browser compute and keeps website sessions on the user's computer. Vercel serves the frontend while the bridge owns the persistent interactive connection. See [Vercel function limits](https://vercel.com/docs/functions/limitations).

Remote access requires the computer to remain awake and a secure route to the bridge. A user-controlled HTTPS tunnel or private network can provide this. Cloudflare's [Quick Tunnels](https://developers.cloudflare.com/tunnel/get-started/quick-tunnels/) are an evaluation option with availability and concurrency limits. They are not a production service-level guarantee. `keep-safe setup` opens the tunnel as its default route, says so, and `keep-safe status` shows the address. `--route tailscale` and `--route local` avoid it.

## Data and lifetime

- Owner and agent bootstrap tokens plus Web Push keys are local files with owner-only permissions in ignored `.keep-safe/`.
- Offline key replacement requires an exclusive configuration-directory lock shared with the bridge CLI. It never prints new keys. Owner/all replacement durably revokes remembered phones and subscriptions before committing new bootstrap authority; agent-only replacement preserves them. VAPID keys remain unchanged. A crash lock is retained for explicit recovery rather than stolen automatically.
- Connection diagnostics use a pure existing-config reader and do not acquire or alter locks. Only a fixed loopback `/api/info` check receives the owner key. Public HTTP/preflight/WebSocket probes are unauthenticated, reject redirects, bound responses, and report transport rather than ownership or physical-phone success. The setup helper prints commands without reading keys or starting a tunnel.
- The default MCP client uses a private direct HTTP agent for loopback URLs, keeping the agent key off global proxy dispatchers. Explicit custom-fetch injection remains an integration responsibility; remote HTTPS uses the normal fetch transport. Redirects are refused.
- Paired phones receive separate device keys that expire 30 days after their last use. The bridge stores SHA256 digests and device metadata in a local, atomically written file. It does not retain raw device keys.
- A device key is saved in the phone's localStorage when the phone pairs with a code, or after explicit opt-in when connecting with the owner token. The master owner token remains tab-only. Authenticated APIs and every live-control message recheck expiry/revocation. The device key never confers agent rights or permission to pair another phone.
- Request metadata is in memory and resets on restart. Eligible finished records are removed automatically 24 hours after original expiry, or earlier by confirmed owner cleanup/capacity pressure. All unexpired outcomes and pending browser opening/finalization/input/closure remain protected. A tracked failed close retains its browser reference for retry. The 100-record cap refuses new requests when no safe record can be removed.
- Web Push subscriptions may be stored locally. They are not uploaded to Vercel.
- Browser input is relayed transiently. Passwords and input messages are not logged or written to disk. Screenshots are streamed without recordings or trace files.
- Managed browser cookies remain in an isolated in-memory context. Existing agent browser cookies remain owned by that browser.
- Handoffs expire after ten minutes by default, with an agent-requested maximum of thirty minutes. Owner control ends on completion, denial, or expiry. A completed managed browser remains available only until the original deadline.

## Controls and limits

The bridge validates request URLs, accepts loopback-only CDP endpoints, rejects unsupported message types, bounds message sizes and queue length, checks permitted frontend origins, and limits request/input rates. Only one owner connection can control a given request at a time. Managed browser traffic passes through a local proxy that resolves and validates DNS, rejects private and reserved addresses, and connects to the validated IP. Subresources and redirects use the same boundary. External CDP browsers remain outside that managed network boundary.

Owner pairing links are sensitive credentials. Share them only with yourself. The app supplies revocable phone keys but does not provide a multi-user account service. Closing a tab is not equivalent to revocation. Use Connections to revoke a phone; possession of the original private owner link remains bootstrap authority.

An agent must cooperate by pausing while the human has control. Keep Safe cannot stop a separate process from issuing its own CDP commands. An agent holding the debugging endpoint has privileged access to that browser; do not use a general personal browser profile for untrusted agents.

## Notification routing

Notifications identify an exact request and the bridge's existing public VAPID key. This is a routing hint checked against authenticated metadata, not authentication or proof of a unique physical computer. Copied configurations can share a public key. No pairing token, private notification key, browser input or private bridge URL is included in an intent.

The new payload nests the versioned intent so an older worker cannot turn its top-level request ID into an unscoped target. The updated worker uses a new message type and fragment names, scopes notification tags by source, ignores supplied destination URLs and picks at most one eligible top-level app window. If that window is paired to another computer, the app gives guidance instead of navigating another tab or changing pairing. Legacy and malformed fresh entries have an explicit neutral marker, preventing desktop startup from opening the first approved browser by default. No fetch handler caches credentials or frames.

The app verifies fresh source-scoped metadata and the exact unexpired request, with connection, interaction, rendered-view and pending-intent identity checks around asynchronous work. A source switch or newer intent invalidates old results. Unknown IDs never fall back to another queued request. A notification during another live browser offers an explicit Open request action that revalidates before leaving and discarding its local draft. Fresh remembered-phone entry stays neutral until checks succeed. Legacy, missing and wrong-source alerts preserve the current warm view and show guidance; they never approve or pair automatically.

New worker messages/fragments are ignored by cached older apps, and the new app treats legacy worker messages as guidance. An untouched older app plus older worker cannot be repaired by a new push payload alone. Finish any active handoff, update the bridge, close all Keep Safe tabs/app windows and reopen. A worker update can wait while old pages remain open; refreshing a single page is not sufficient, as described in the [service worker lifecycle](https://web.dev/articles/service-worker-lifecycle#waiting). Automated worker and app routing checks do not establish OS notification display or physical-phone delivery.

## Authentication method limits

The phone interacts with the remote Chromium page. This does not move a phone's passkeys, native password manager, biometrics, or hardware security key into that remote browser. Some sites also block automated browsers. These methods need explicit testing and may require a supported cross-device authentication flow.

Use a separate browser profile, and inspect the current website origin before entering credentials. The app shows the live scheme, hostname, and port without the URL's path, query, fragment, or credentials. A change of origin triggers a warning, including HTTPS to HTTP or a different port. Opaque pages such as `about:blank` are not labeled as HTTPS. Keep Safe does not bypass website authentication or anti-abuse protections.

On mobile, leaving request details releases live control and stops frame streaming. Pending wheel input is discarded when leaving, changing requests, disconnecting, or ending control. Reopening the request can resume its existing browser before expiry.

On `visibilitychange` to hidden or `pagehide`, the workspace synchronously gates new browser actions, invalidates the current socket and frame, preserves pending/failed focus protection, and closes that control connection. A replacement authenticated socket receives queue and revocation updates without watching a browser. Old socket callbacks cannot restore a frame or acknowledge focus. Returning through visibility/pageshow does not resume control; an explicit resume validates the current logical request, connection and original expiry, starts a fresh transport and requires a new image before any input. Resume also requires renewed focus confirmation or an intentional browser tap/Tab, since another owner or the website could have changed focus while paused.

The phone discards its local text draft, reveal setting and input disclosures on those lifecycle signals, and clears drafts on request, connection or live-URL changes. A paused view has no remote image or input controls. This is best-effort browser lifecycle handling, without an OS app-switcher or physical suspension guarantee. The website continues running on the developer's computer. Explicit Done remains available when connected; pausing itself never completes or denies the request.

Closing a socket releases its controller out of band, while already running browser operations keep the existing entry barrier. The server drops queued commands once their socket is closed; otherwise a delayed watch could reclaim ownership after the close event. A subsequent owner waits for accepted work to settle. Explicit handback still drains that work and verifies password clearing before exposing an agent endpoint.

Bridge shutdown sets its stopping flag before awaiting browser cleanup, refuses new WebSocket upgrades with HTTP 503 and discards queued socket commands. This prevents a reconnect from joining after existing clients were terminated and keeping WebSocket shutdown pending. A held-cleanup regression verifies rejection before releasing the browser's close operation.

Website Back, Forward and Reload are owner-only managed-browser operations. The phone synchronously invalidates its image, controls and local draft, blocks input/inspection/focus/Done, and requires a correlated result plus an image bearing the new server epoch. Previously started captures cannot restore old geometry. Same-URL reload also resets local text and focus. Unconfirmed navigation pauses control without automatically repeating the action; handback then requires explicit Resume and a fresh image. The server keeps actual browser work in the request's handback barrier, including its stop-loading request and renderer settlement. Concurrent browser-close calls share the actual cleanup promise, so navigation failure and expiry cannot treat a still-running close as complete.

Before departure, navigation binds the current page/document and numeric history entry, clears current password fields and rejects a changed destination binding. A temporary context route blocks non-GET/HEAD document requests so Reload cannot silently resend a form. An installed-Chromium counter-only probe reproduced POST resubmission without a dialog. Chromium's [CDP Reload handler](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/devtools/protocol/page_handler.cc) passes false for repost checking, while the [navigation controller](https://chromium.googlesource.com/chromium/src/+/refs/heads/main/content/browser/renderer_host/navigation_controller_impl.cc) conditions repost confirmation on that flag. Managed contexts block service workers and pinned [Playwright 1.64.1 disables back/forward cache](https://github.com/microsoft/playwright/blob/v1.64.1/packages/playwright-core/src/server/chromium/chromiumSwitches.ts) for history interception. Attached browsers cannot supply these guarantees and do not advertise navigation. This blocks document resubmission, not arbitrary requests a website makes through its own JavaScript. Clearing the current document does not sanitize all prior browser history or website-retained JavaScript state.

The live image supports one-finger swipe scrolling after an eight-CSS-pixel movement threshold. Coordinates are scaled to the streamed viewport; batches are bounded to 3000 pixels and spaced at least 50ms apart, without inertia. A batch is tied to the current request, connection, URL, intrinsic geometry and control interval. Known changes, display resizing, hidden/blurred pages, capture loss and multi-touch discard pending input. Screenshot refreshes alone do not change the interval. Short completed taps have a separate path, with compatibility-click suppression; scrolling never confirms a failed field focus.

The image permits host pinch zoom using [`touch-action: pinch-zoom`](https://compat.spec.whatwg.org/#touch-action); ctrl-wheel remains local. Explicit click guards are needed because cancelling a pointer event does not by itself suppress click events under [Pointer Events](https://www.w3.org/TR/pointerevents3/#compatibility-mapping-with-mouse-events). Tests exercise trusted Chromium touch input; physical-device and assistive-technology behavior remain unverified.

Optional paired scroll positions are authenticated and validated against the last frame size. A position moves the browser pointer without clicking before wheel input, so nested panels and embedded pages can receive it. Both operations use one captured page and the existing input barrier. A known page/URL change while positioning aborts the scroll rather than applying it to a new popup. Unanchored clients retain their previous wheel behavior; older bridges do not provide positioned scrolling.

The owner may request a bounded control list over the authenticated live-control socket, including native controls in nested open roots and supported HTTP(S) frames. Only the active controller receives labels/roles/state; field values, cookie data and link addresses are not inspected. The browser retains at most 50 transient target handles across all documents, bound to a snapshot, page, exact frame/URL and private composed ancestry. Navigation, refresh, handback, root/ancestor or frame replacement and closure invalidate them. Focus rechecks the current descriptor, deep open-root active element and actual active iframe chain up to the top document. The frontend requires the matching acknowledgement before reporting success. The HTML focus model retargets document-level focus to a component host; see the [HTML focus specification](https://html.spec.whatwg.org/multipage/interaction.html#focus). Website-provided labels can still contain sensitive text; this is transient owner-visible content, never activity history or a server log. Pending inspection/focus participates in the handback barrier. This is an approximate control navigator rather than full accessibility-tree or physical assistive-technology support.

Control traversal is incremental, bounded per document to 3,000 DOM nodes, 200 candidate controls, 100 open roots, 64 DOM levels, 24 nested shadows and 50,000 work steps. The complete inspection shares a two-second deadline and visits at most 12 documents including the top page, to child depth four. Names remain limited to 160 characters and use root-scoped label references. A truncated scan reports its actual result count. Native DOM/layout work can still block the renderer; invalidation does not abandon the input barrier while that work is pending.

Clients must send literal `includeFrames: true` to request embedded results. Legacy clients receive a main-only list. Embedded entries add only `embedded: true` and `frameOrigin`; the snapshot's origin remains the top page. Exact frame URLs are private bindings, never returned as control metadata. Each iframe host and its composed ancestors must remain visible, enabled and bound to the same frame. Frames with `sandbox`/`srcdoc` attributes, opaque origins and unsupported schemes are omitted with their subtrees. Same-process child navigation intents use the ancestor CDP channel; out-of-process frames get a separate guard and same-channel barriers. A different origin alone does not prove a separate renderer process. Retired focus snapshots keep their channels until all queued work settles.

Frame eligibility must account for the actual security origin. `Window.origin` is page-writable, `location.origin` is URL-derived, and Chromium's CDP frame-tree `securityOrigin` can still report a URL precursor for an opaque response-CSP frame. Each separate guard identifies its root frame exactly; in-process child matching conservatively checks every matching private URL. Opaque or conflicting duplicates are omitted. The metadata walk is bounded to 256 entries. A response CSP sandbox without `allow-same-origin` is opaque even without an iframe attribute; a non-opaque response policy is not rejected solely for being a sandbox policy.

The additional read-only `Storage.getStorageKeyForFrame` probe rejects actual opaque origins in Chromium's browser process. Its returned key is immediately discarded, never logged or exported; no storage contents or cookies are read. Missing/failed eligibility results omit the candidate. See Chromium's [storage handler](https://chromium.googlesource.com/chromium/src/+/main/content/browser/devtools/protocol/storage_handler.cc) and [page agent](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/core/inspector/inspector_page_agent.cc) for the distinction. Installed-browser regressions cover response-CSP opacity, a spoofed or throwing page origin property, and conflicting duplicate frame URLs.

Password handback cleanup scans all session pages/frames and their open roots, including hidden password fields. It uses the native input setter, sends input/change events and checks only empty/nonempty booleans in the browser, with a separate verification round trip. A final read-only pass verifies the complete page/frame set after all clearing events, so a later handler cannot silently restore an earlier field. Page/frame identity and document-generation checks require a stable set. Traversal is bounded to 100,000 elements per pass, 1,024 roots, 32 nested roots and 4,096 password targets under a shared three-second handback deadline. Errors, exhausted budgets and immediate field reinsertion withhold handback. Closed roots and secrets retained by destination JavaScript are not inspected or erased. This cleanup is separate from the optional control list and does not export input values.

Each tracked page also has a lifetime CDP `Page.windowOpen` monitor, armed before owner input, frames or control inspection. Managed initial navigation waits for its monitor too. It ignores event payloads. Same-channel renderer barriers check unresolved window intents before and after clearing, because Playwright can omit a popup while its first navigation is pending. An unresolved intent or new intent during clearing withholds handback; after the popup becomes available, an explicit retry can clear it. Changed page sets are rescanned within the same deadline. Busy renderer work retains its barrier rather than being abandoned on a timer. Activity before a page becomes tracked, including a hidden popup's own earlier descendants, and arbitrary future website tasks are outside this verification boundary. A blocked or never-published window intent can conservatively keep handback blocked until the request ends.

## Notifications

The bridge can use Web Push with locally generated VAPID keys. Permission is requested only when the owner enables notifications. Some mobile browsers require installation to the home screen. Actual lock-screen delivery requires a subscribed physical device and is separate from testing the service worker and subscription API. On iOS, install to the Home Screen before requesting push from a user gesture; see [WebKit's Web Push guidance](https://webkit.org/blog/13878/web-push-for-web-apps-on-ios-and-ipados/).

Enrollment status and removal accept a complete browser subscription over the authenticated owner API. The endpoint, both encryption keys and exact owner/device principal must match; the response exposes only a boolean or acknowledgement. Authority is rechecked after reading a request body. Removing an enrollment preserves pairing and the browser subscription so other computers using that same subscription are unaffected. Dead provider endpoints are removed durably, and a delayed rejection cannot remove a newer enrollment at the same endpoint.

The explicit Remember action may transfer a positively verified master enrollment to its newly issued device principal. It supplies only the current browser subscription, checks record identity again after persistence, and does not publish the device token until migration succeeds. Failure removes the unpublished device and attempts both rollback writes without overwriting a concurrent replacement. Two separate files cannot provide an atomic transaction under a permanent filesystem failure; any orphan device token from such a failure is unpublished. No migration runs merely because the active connection changes.

The app rechecks enrollment for its current pairing on connection, visibility and focus changes. Late responses from an earlier pairing cannot change the current status. A browser subscription belongs to the app's service-worker registration, not to an individual bridge. Replacing a different application-server key requires explicit confirmation because the old subscription must be removed first, as specified by the [Push API](https://www.w3.org/TR/push-api/). This is separate from normal per-computer removal. Neither enrollment nor a successful provider response proves physical-phone delivery.
